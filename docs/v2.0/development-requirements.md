# v2.0 Development Requirements(開発要件)

v2.0 の中心は、**開発環境を整えること**。開発は**ローカル**で行い、ローカルでテストしてから本番にデプロイする。クラウド上に dev 環境は作らない。

この文書は、要件と、決めたこと、まだ決めていないこと(提案つき)、作業の分け方をまとめる。実装はこれから。

## 1. 位置づけとルール

| 項目 | 内容 |
| --- | --- |
| v1.0 | 本番環境に載せるところまで(機能と画面。本番は Workers + Neon + Hyperdrive + Resend) |
| v1.5 | 現状の課題の修正。**担当者が別に対応する。v2.0 には入れない** |
| v2.0 | 開発環境の整備(この文書) |
| 対象外 | ホームなどの Figma 照合・UX の改善(デザイナーが Figma で進めている。確定後に別途) |
| 未定 | 機能の追加(進行確認・ステータスなど)。[要件定義 5 章](../requirements.md)と[申し送り](../v2-todo.md)を、v2.0 に含めるか(D6)。挙がっている候補は [8 章](#8-追加機能の候補d6)(セクション機能、カレンダー機能) |

### 方針

- **開発はローカルの DB で行う。** 開発用の DB は、ローカルの dev 用コンテナ(Postgres)。
- **Neon(本番)には、デモ用に作ったデータだけを置く。** 開発中のデータや、検証用のデータは上げない。
- **流れは「ローカルでテスト → 本番にデプロイ」。** クラウドに dev 環境(dev 用の Workers や Neon)は作らない。そのため、環境ごとの `wrangler` の分割、dev 用のアクセス制限、PR ごとのプレビューは、v2.0 では扱わない。

### ブランチの運用

- `dev` ブランチは残す。v2.0 の作業は **`dev` から切り、`dev` に向けて PR を出す**。`main` へは、これまでどおり `dev` からのリリース PR でまとめる。
- **v2.0 のブランチ名には `v2` を付ける。** 形式は `<種類>/v2/<内容>`(例: `infra/v2/local-dev-container`、`ci/v2/deploy-workflow`、`docs/v2/...`)。ブランチ名だけで、v1.5 の修正と区別できるようにする。

## 2. 現状(v1.0 の環境)

| 項目 | ローカル | 本番 |
| --- | --- | --- |
| web / api | `vite dev` / `bun run dev` | Cloudflare Workers(`ningyoutukai-web` / `ningyoutukai-api`)。web が `/api/*` を api にサービスバインディングで転送(同一オリジン) |
| データベース | docker compose の Postgres 17(ポート 5433。`api/docker-compose.yml`) | Neon(シンガポール、Postgres 18、DB `neondb`)。Workers からは Hyperdrive 経由 |
| 認証 | GitHub / Google の OAuth アプリ | **同じ OAuth アプリを共用**(GitHub のコールバック URL を本番向けに書き換えたため、ローカルの GitHub ログインは、書き戻すまで使えない) |
| メール | 未設定(ログのみ) | Resend(送信元 `noreply@mail.maars.dev`、送信専用キー) |
| デプロイ | - | 手元から `wrangler deploy`(手動)。`api` を先に、`web` を後に |
| CI | GitHub Actions(`ci.yml`: 型検査・テスト・ビルド) | `migrate.yml`(手動実行)、`backup.yml`(定期実行)もある |

分かっている課題(v2.0 で扱うもの):

- **ローカルの DB が本番とずれている**(ローカルは Postgres 17、本番は 18)。
- **API のテストが、開発用の DB に対して実行される。** テストは自分のデータを作って消す作りだが、専用のテスト用 DB がなく、開発中のデータと同じ DB を使う。
- **認証が環境で分かれていない**(OAuth アプリの共用)。
- **ローカルの手順が、README とコンテナの設定に散らばっている。** 新しい人が、コンテナの起動から、マイグレーション、起動、テストまでを、一通りたどれる手順がほしい。
- **「テスト → デプロイ」の手順が、手元の手作業**(マイグレーション → api → web)。

## 3. 目標の環境

| 環境 | 用途 | web / api | DB | 認証 | メール |
| --- | --- | --- | --- | --- | --- |
| local(dev) | 開発とテスト | 手元(`vite dev` / `bun run dev`。必要なら `wrangler dev` で Workers 上の挙動も確認) | dev 用コンテナ(Postgres 18)。開発用の DB と、テスト用の DB を分ける | 開発用の OAuth アプリ(コールバックは `localhost`) | 送らない(ログに宛先・件名・本文を出す) |
| production | 本番(デモ用のデータのみ) | Workers(`ningyoutukai-*`) | Neon(本番) | 本番用の OAuth アプリ | `noreply@mail.maars.dev` |

```
  ローカル(dev 用コンテナ)                                  本番
  開発 → テスト(型検査・テスト・ビルド・マイグレーション)  ─▶  マイグレーション → api → web
        ↑ dev 用 DB / テスト用 DB                                  Neon(デモ用のデータ)
```

## 4. 要件

優先度: **Must**(v2.0 に必須)/ Should(できれば)/ Could(余裕があれば)。

| # | 優先度 | 要件 | 受け入れ条件 |
| --- | --- | --- | --- |
| R1 | Must | **dev 用コンテナ。** `docker compose up` で、開発に必要なコンテナが上がる。Postgres は**本番と同じメジャー版(18)** | コマンド 1 つで起動し、ヘルスチェックが通る。データはボリュームに残る。既存の Postgres 17 のボリュームからの移行手順がある |
| R2 | Must | **テスト用の DB を分ける。** テストは、開発用の DB ではなく、専用のテスト用 DB で実行する | テストの実行が、開発用の DB のデータに触れない(件数が前後で変わらない)。テストの前に、マイグレーションが自動で適用される |
| R3 | Must | **認証の分離。** ローカル用と本番用で、OAuth アプリを分ける。`BETTER_AUTH_SECRET` も別 | ローカルで GitHub / Google のログインでき、本番のコールバックを書き換える必要がない。設定手順が文書にある |
| R4 | Must | **メールの安全。** ローカルから、実在のユーザーにメールが送られない | ローカルでは送信されず、宛先・件名・本文がログに出る(`RESEND_API_KEY` を設定しても、ローカルでは送らない切り替えがある) |
| R5 | Must | **「テスト → デプロイ」の手順。** ローカルでテスト(型検査・テスト・ビルド・マイグレーションの確認)に通ったものを、本番にデプロイする | 手順(マイグレーション → api → web → 確認)が、1 つの手順書と、1 つのコマンド(またはワークフロー)にまとまっている。失敗したとき、前のバージョンに戻せる |
| R6 | Must | **マイグレーションの順序。** ローカルの DB に先に適用してテストし、そのあと本番に適用する。本番に適用する前に、バックアップ(ダンプ)を取る | 破壊的な変更(列の削除など)の進め方が決まっている。本番への適用が、バックアップの確認つきの手順になっている |
| R7 | Must | **手順書。** ローカルの開発環境の構築、テスト、デプロイ、復元を、手順書にする | 新しい人が、手順書だけで、ローカルの開発環境を構築し、テストを通せる |
| R8 | Should | **デモ用のデータ(シード)。** ローカルと本番に、デモ用のデータを入れるスクリプトがある | コマンド 1 つで、デモ用のユーザー・プロダクト・タスクが入る。再実行しても壊れない |
| R9 | Should | **バックアップの復元訓練。** 本番(Neon)のダンプを R2 から取り出し、ローカルの dev 用コンテナに復元して確認する | 復元の手順と、確認の結果(行数の一致)が記録されている |
| R10 | Should | **Workers 上の挙動の事前確認。** デプロイの前に、`wrangler dev`(ローカルのコンテナの DB に接続)で、Workers 上の挙動を確認する | 手順書に、確認する項目がある(ログイン、書き込み、トランザクション) |
| R11 | Should | **本番のログと障害の把握。** `wrangler tail` や Workers Logs の見方が手順書にある | 障害のとき、原因をたどれる |
| R12 | Should(D10 で決定。v2.0 の最初に行う) | **ローカルのメール受信箱。** Mailpit のようなコンテナで、送るはずだったメールの見た目を確認できる | メールの内容を、ブラウザで見られる |
| R13 | Must | **費用を無料枠に収める。** 追加の費用が出る項目は、事前に費用を示して確認する | 構成の各項目に、費用の目安と、無料枠の上限が書かれている |
| R14 | Should | **web の API 呼び出しを Eden(Elysia の型共有)にする。** いまは `web/src/lib/api.ts` で、api の応答の形を手書きの型にして `as T` で当てており、api を変えても web の型エラーにならない。api の型を web が直接使い、変更が型エラーとして web に出るようにする | 全 API の呼び出しが Eden 経由になり、手書きの応答の型(`ProductSummary` など)が無くなる。api の応答やリクエストの形を変えると、web の `tsc` が失敗する。同一オリジン(ベース URL が空)とエラーの扱い(`ApiError`)は、いまと同じ挙動 |
| R15 | Should | **ログイン後のデータ取得の調査(調査のみ)。** ログインしてからデータが出るまでが、体感で約 3.1 秒かかる(報告)。どこに時間がかかっているかを調べ、結果を記録する。**最適化の実装は、この要件に含めない**(調査の結果を見て、別に決める) | ログインの内訳(アプリのログインボタン、認可画面、プロバイダからの戻りの callback、`/home` 以降の取得)ごとの時間が、記録されている。縮められる部分と、外部のプロバイダとの通信など縮められない部分が、分けて書かれている |

#### ログイン後のデータ取得の調査の進め方(R15)

すでに分かっていること(本番、ログインなし、この PC から測定):

- 画面の HTML は 55〜62 ms(約 3.8 KB)。サーバーの返答は速い。
- API の往復は、約 30〜60 ms。報告では、ログイン後の画面遷移は約 40 ms。
- 初回に読む JS と CSS は、非圧縮で 423 KB(最大は `index` の 283 KB)。
- `/home` の HTML は、中身が空の骨組み。データは、ブラウザで `get-session` → プロダクト一覧・招待 →(プロダクトの画面は)ツリーの順に取る。
- 報告されたログイン → データ取得の全体は、約 3.13 秒。**どこまでがプロバイダ(GitHub、Google)との通信かは、未計測。**

調べること:

1. ログインの流れを、開発者ツールの Network(Preserve log)で、リクエストごとに計測する(`sign-in/social`、プロバイダの認可、`callback/...`、`get-session`、`product`、`invitation`、`tree`)。
2. callback の中で、プロバイダとの通信と、DB の書き込みが、それぞれ何 ms か(サーバー側の計測が要る場合は、ログに時間を出す)。
3. ログイン済みで `/home` を開き直した時間(OAuth を除いた分)。
4. 結果から、アプリ側で縮められる部分(取得の並列化、`loader` でのサーバー側取得、キャッシュ、JS の分割など)が、あるかを書く。

#### Eden の試作で確かめる点(R14)

- **web が api の型を読めるか。** web の `tsc` が api のソース(Bun、drizzle、better-auth の型)ごと読むため、遅くならないか、`tsconfig` が衝突しないか。難しければ、api 側で型の宣言ファイル(`.d.ts`)を出し、web はそれを読む。
- **日時の型。** DB から返る日時は JSON では文字列。Eden の型が `Date` になって、実際は文字列という食い違いが起きないか。
- **応答の型が出ているか。** ルートに応答のスキーマ(`response`)が無いと型が緩くなる。26 本のうち、無いものを洗い出す。
- **エラーの形。** いまの `ApiError`(`{ message }`)と、Eden のエラーの扱いを合わせる。
- **同一オリジン。** web の Worker が `/api/*` を転送する構成で、ベース URL を空にできるか。

## 7. 完了の定義(v2.0)

- R1〜R7、R13(Must)が満たされている。
- `docker compose up` で、dev 用コンテナ(Postgres 18)が上がり、開発用の DB とテスト用の DB が分かれている。
- テストが、開発用の DB のデータに触れない。
- ローカルでログインでき、メールは送られない。
- 手順書どおりに、ローカルでテストして、本番にデプロイできる。本番のマイグレーションは、ローカルで一度通ったものだけを適用している。

## 8. 追加機能の候補(D6)

環境の整備(1〜7 章)が終わってから、v2.1 以降で扱うかを決める。ここでは、挙がっている機能と、決まっていること、確認することを残す。**F3 は、v2.0 の範囲と決まっている。** F1・F2 は、v2.0 に含めるかが未定。

### F1. セクション機能

- メンバーを、**セクション**に入れられる(メンバーごとに、所属するセクションを持つ)。
- **セクションを作れるのは、リーダーのみ。**
- 注意: [要件定義](../requirements.md)の「セクション」は、機能を画面ごとに分けた呼び方で、この機能とは別。

### F2. カレンダー機能

- **納期を決めると、Google カレンダーに自動で日程が追加される。**
- **納期を決められるのは、リーダーのみ。**

### F3. タスク納品補足(**v2.0 の範囲**)

- **完了報告に、メッセージをつけて送れる。** 似た機能は、GitHub の PR のコメント。
- **決まったこと**: PR のコメントにほぼ近い形にする。つまり、(1) 報告のあとも、担当者とリーダーがメッセージを書き足していける(**やり取りの履歴を持つ**)。(2) リーダーは確認(承認)のほかに、**差し戻し**ができ、担当者は**再提出**できる。
- **決まったこと(見える人)**: PR と同じで、**公開しているタスクの場合、コメントも誰でも見られる**。タスクの公開・非公開(`isVisible`)に、コメントの見え方を合わせる。非公開のタスクは、いまの `canSee` と同じく、リーダーと担当者だけが見られる(提案)。
- 設計への影響(提案): メッセージ用のテーブルを新しく持つ(タスク、書いた人、本文、日時)。完了までの流れは「報告 → 確認」の一方向から、「報告 → 確認 または 差し戻し → 再提出 → …」の繰り返しになる。`tasks.reportedAt` の意味(いまは「報告済み」)と、差し戻し中の状態の持ち方を決める必要がある。
- いまの完了報告(`POST /api/product/:productId/task/:taskId/complete-report`)は、`reportedAt` を記録し、リーダーへメールを送るだけで、本文を持つ場所がない。報告できるのは担当者本人のみ。

| # | 機能 | 確認すること |

| Q1 | F1 | 1 人のメンバーは、複数のセクションに入れるか。プロダクトをまたいだセクションはあるか(プロダクトごとか) |
| Q2 | F1 | セクションの使いみちは何か(ツリーの表示をセクションごとにまとめる、タスクをセクション単位で割り当てる、など) |

| Q4 | F2 | 日程が追加される先は、誰のカレンダーか(タスクの担当者、リーダー、両方) |
| Q5 | F2 | Google カレンダーへの書き込みの許可は、どう取るか。ログインとは別に、カレンダーの権限(スコープ)を追加で求める。GitHub でログインした人には、Google の連携が別に必要 |
| Q6 | F2 | 納期の変更・タスクの削除・完了のとき、カレンダーの予定も、更新・削除するか |

| Q8 | F2 | Google の審査(カレンダーの権限は、公開するアプリでは確認が要る場合がある)と、無料枠の範囲に収まるか(R13) |
| Q9 | F3 | **決定済み**: PR のコメントのように、やり取りの履歴を持つ(報告のあとも、担当者とリーダーが書き足せる) |
| Q10 | F3 | メッセージは必須か、任意か。文字数の上限と、書式(プレーンテキスト、Markdown)、添付(画像・ファイル・URL)の有無 |
| Q11 | F3 | **決定済み**: 差し戻し(再提出)をつける。残る確認: 差し戻しには、メッセージを必須にするか。差し戻し中のタスクは、ツリーでどう見せるか。再提出の回数に制限はあるか |
| Q12 | F3 | **決定済み(一部)**: PR と同じで、**公開しているタスクのコメントは、誰でも見られる**(タスクを見られる人は、コメントも見られる)。残る確認: 非公開のタスクは、いまのタスクの見え方に合わせて、リーダーと担当者だけが見られる形でよいか(提案)。コメントを書ける人は、公開タスクでも、リーダーと担当者だけか、見られる人全員か |
